## What this is

A **test harness for Atlas core**, not a product: a password-manager-shaped client that proves core's shared logic — `@atlastodo/client-core`/`@atlastodo/sdk` from npm (including `sealPersistence`), the `atlas-client` crate and the server's vault token policies — works for an app other than todo. The web app has no releases, no store presence and no native builds, and must not hold real secrets. What is released here is the vault's command line for CI: the `atlas-vault` CLI and `secretspec-provider-atlas` (`crates/`), which took over core's `atlas vault …` commands and SecretSpec provider. The server, the engine crates and the core packages are in the core repository, [atlastodo/atlas](https://github.com/atlastodo/atlas) (a checkout is expected at `../atlas` by the scripts).

- Bumping the core pin here is how a core change is exercised from the outside: move it, run `test:all`, `lint` and `e2e:cli` (and `E2E_WEB=1`). A failure is a finding about core; fix it in core (a branch in the core repository), not with a workaround here.
- Removed on purpose (2026-10): the Android/iOS build (devenv Android SDK, `build:android*`, `mobile:*`, the Gradle cache workflow and action, EAS, the native Argon2 module, the keychain session, SQLite persistence, the install key, the clipboard's Android flag, store icons and splash), the Android permission allowlist, the app's release tooling, `version:bump`, release notes, the derived `versionCode` and the web release tarball. Don't bring them back. `release.yml` is the Rust binaries' alone (see CI).

## Dev environment

- All dev commands (`test:all`, `e2e:cli`, `lint`, `fmt`, `nix:bun-lock`, `deps:update`, `web:dev`, `web:export`) are devenv scripts in `devenv.nix` — run them inside `devenv shell` (or `devenv shell -- <script>`). The root `package.json` has **no** scripts. (The full suite is `test:all`, not `test`, which collides with the shell builtin.)
- Bun is the package manager (`bun.lock` committed, lockfile version 1 — bun2nix reads no other; CI installs with `--frozen-lockfile`); Node 26 is the runtime. Bun is pinned to **1.4.4** in devenv (the flake's nixpkgs, which `devenv.yaml` follows) and `.bun-version` (which every `setup-bun` in CI reads with `bun-version-file`), in lockstep: `deps:update` moves both to the Bun that nixpkgs ships. No version pin lives in `.github/`: the weekly refresh pushes with the workflow token, which may not change workflow files.
- One set of pins: `devenv.yaml` takes `nixpkgs` from this repository's flake (`atlas-vault: url: path:.`, `follows: atlas-vault/nixpkgs`), so the shell and the flake's builds share `flake.lock`. Move it with `nix flake update`, then `devenv update` (which copies it into `devenv.lock`); `lint` and CI's `Lint (TypeScript)` fail when `devenv.lock` is behind (`scripts/check-devenv-lock.mjs`).
- Rust: nixpkgs' in devenv (`languages.rust`), `rust-toolchain.toml`'s (an exact version, kept with core's) in CI and the release builds; the MSRV is `Cargo.toml`'s `rust-version`. Core's `atlas-client` and `atlas-core` come by git tag (`Cargo.toml`), never a path. devenv also ships the real `secretspec` (nixpkgs), which `e2e:cli` drives the provider with.
- TypeScript is 7 (the native compiler) everywhere: the root and both workspaces. Its npm package has no JS compiler API, which is why the linter is oxlint, not ESLint with typescript-eslint.
- The core packages come from npm at an exact version: `@atlastodo/client-core` and `@atlastodo/sdk` (`VaultClient`'s `AtlasError` and the SDK's test `FakeServer`); core's crates come from the same release's git tag (`Cargo.toml`). They follow the newest core release (rc or stable), moved together by `deps:update` (Dependabot ignores them) (the e2e job in `ci.yml` reads the npm pin for its server image). Core's `field_policy_vectors.json` is read from client-core's package, so a bump picks it up; `test-vectors/` (the item rules' `vault_item_vectors.json` and the CLI's `cli_golden.json`) are this repository's own.
- A server for development: in the core checkout, `devenv up` and `ATLAS_APPS=todo,vault cargo run -p atlas-server`; `EXPO_PUBLIC_API_URL` defaults to `http://localhost:8080`.

- Nothing is held back on purpose. Dependabot (`.github/dependabot.yml`, weekly, to `dev`, a 3-day `cooldown`) covers direct dependencies (Bun, Cargo but core's crates), the Rust toolchain and Actions; everything else (`devenv.lock`, `flake.lock`, the Bun pins, the whole `bun.lock` and `Cargo.lock` with transitives and the `overrides`, the Expo SDK's packages via `expo install --fix`, the core pin and core's crates, `nix/bun.nix`) is `deps:update` (`scripts/update-deps.sh`), which `deps-refresh.yml` runs weekly and opens as one PR from `chore/deps-refresh`. A new Expo SDK major is a migration, flagged as an issue. `overrides` are ranges, never exact pins.

## Verification

- `test:all` = `cargo nextest run --workspace` → vitest in `packages/vault-core` (under Bun: `bunx --bun vitest run`) → jest-expo in `apps/vault` (must run under real Node: `bun run test`).
- `lint` = `cargo fmt --check` + clippy (`--no-deps -D warnings`) + `tsc --noEmit` for both workspaces + `oxlint .` (`.oxlintrc.json`: the typescript-eslint `recommended` rules and react-hooks `rules-of-hooks` (error) and `exhaustive-deps` (warning)) + `prettier --check .` + `scripts/third-party-licenses.mjs --check` + a stale-`nix/bun.nix` check.
- `e2e:cli` (`scripts/e2e-cli.sh`) = a throwaway database, core's `atlas-server` with `ATLAS_APPS=todo,vault`, the `atlas-vault` CLI and `secretspec-provider-atlas`: their own end-to-end tests (`crates/*/tests/e2e.rs`, `#[ignore]`d without a server, run with `--run-ignored all` and `ATLAS_E2E_SERVER`; the provider's last one drives the real `secretspec` from `SECRETSPEC_BIN` or `PATH` and returns early without one), then `packages/vault-core/e2e` proves an item the CLI adds shows up in the app's store field for field and the reverse (edits, secret history, trash), that `atlas-vault get X --field password` prints exactly what the app stored, that a read-only token made as the app makes it is refused writes by the server (a raw push: 403 `api_token_read_only`), that the server's token-policy errors come back typed, and that an Atlas Todo account gets its vault key on its first vault sign-in. `E2E_WEB=1` also exports the web app, serves it from that server and drives it in headless Chromium (`scripts/e2e-web.mjs`: sign-up, a login with its password masked, search, read-only and writing tokens made in Settings, the CLI both ways, an item written while the sync routes fail surviving a reload and syncing after, the vault's IndexedDB holding no plaintext, lock/unlock, a session past its auto-lock deadline opening locked). The server is built from `ATLAS_CORE_DIR` (default `../atlas`) or given as `ATLAS_SERVER_BIN`, the binaries built here (`ATLAS_CLI` overrides the CLI); Postgres from `E2E_DATABASE_URL` (default the devenv one on 5432). CI's `End to end` job runs the same suites (without the real `secretspec`) against the pinned core release's image and the binaries built from the commit.
- The web app is the only target: `web:export` (or CI's export step) must pass. jest-expo still renders the screens with its default (native) preset; there are no platform files any more, so the web implementations are what the tests run.

## Layout and rules

- `crates/atlas-vault-rules` — the item rules in Rust and `VaultClient` (core's `AtlasClient`, a vault session, with items and folders on top), at parity with `itemRules.ts` through `test-vectors/vault_item_vectors.json` (a rule change needs a fixture both sides pass); its tests run on core's `FakeServer` (`atlas_client::testing`). The vault is personal: it registers no app definition, only core's manifest (`manifests/vault.json`, which stays in core: the server reads it and enforces its token policy).
- `crates/atlas-vault-cli` — the `atlas-vault` binary: the same environment, JSON output and exit codes as core's `atlas` CLI had; commands are flat (`get NAME`) or app-first (`vault get NAME`, the old form). Its output is pinned by `test-vectors/cli_golden.json` (`tests/golden.rs`; `GOLDEN_UPDATE=1` re-records it, sorting every object's keys: re-record only new scenarios and keep the rest as it was).
- `crates/atlas-secretspec` — `secretspec-provider-atlas`, an external SecretSpec provider (the Secret Provider Protocol of SecretSpec 0.21+, through the Apache-2.0 `secretspec-ipc` crate) over a `VaultClient`: project/profile/key are folder/item/field (README, SecretSpec).
- `packages/vault-core` — platform-free: `itemRules.ts` (every item rule: `newVaultItemFields`, `vaultItemChanges` (secret history), `toVaultItem`, …; `@atlastodo/shared`'s `vault.ts` until it moved here, tested on `test-vectors/vault_item_vectors.json`), `client.ts` (`VaultClient`, the headless API-token client for integrations, exported as `@atlastodo/vault-core/client` so the app's bundle leaves it out; the SDK's until it moved here), `items.ts` (items and folders in a client-core `LocalStore` over `itemRules.ts`, never reimplemented; `vectors.test.ts` replays the item vectors through the store), `query.ts` (list filters; search never reads secret values), `generator.ts` (CSPRNG only, rejection sampling, no `Math.random` fallback), `totp.ts` (RFC 6238, tested on the RFC's vectors), `autoLock.ts`, `account.ts` (sign-in/up/unlock, opening the vault app key), `apiTokens.ts` (vault tokens), `engine.ts` (the sealed on-disk store + `SyncClient`).
- **No new crypto.** Keys and envelopes are client-core's: the password opens the root (`openAccountKeys`, `ensureRootKey` for an account without one), the root opens the vault app key (`enableApp`/`openAppKey`, app `vault`). The vault key plays the DEK's role in the keyring (envelope kid `"dek"`, scope personal). The todo key is never stored. If core lacks something, change core (a branch in the core repository), don't work around it here.
- Every sync request is vault-scoped: build clients with `createVaultApiClient` (`x-atlas-sync-apps: vault`). A vault session has no legacy plaintext: `setLegacyMigrated(true)`. The server must offer `api_token_policies` (checked at sign-in, `VAULT_SERVER_REQUIREMENTS`).
- Vault API tokens are vault-only (`apps: ["vault"]`), always carry `expires_at` (≤ the policy's `max_lifetime_days`, from client-core's `tokenPolicyFor`) and send `write` explicitly (false unless the user opts in).
- **Nothing decrypted at rest.** The device's op log (`data/persistence.ts`: IndexedDB `atlas-vault-<user>`, in memory where IndexedDB is missing) is passed to `VaultEngine` unsealed, and the engine always wraps it with client-core's `sealPersistence` under `deriveLocalStoreKey(vaultKey, userId)` — never pass a sealed or plaintext-reading store around it. A log that fails with `SealedStoreError` is cleared (ops, cursor, bootstrap) and pulled again (`onStoreReset`, shown as a notice). `engine.stop()` flushes, closes the database and zeroes the derived key; the vault key bytes are never zeroed (an in-flight push could otherwise encrypt under zeros). `sealedStore.test.ts` covers ciphertext on disk, reopen without the network, the wrong key and offline edits across a restart.
- **Locking** (`AuthContext.lock`, `AutoLockGate`) drops the vault keys from memory and from the stored session, unmounts the vault (its decrypted store, every revealed secret; the engine closes the sealed database) and clears a copied secret. Signing out also deletes the database. The session stores `lockAt`; a session restored past it opens locked. Browser tabs follow each other's lock and activity through the stored session. Auto-lock timeout and clipboard timeout are per-device prefs (`lib/prefs.ts`), not synced.
- Clipboard (`lib/clipboard.ts`): a copied secret is cleared after the timeout; the web cannot read the clipboard without a prompt, so the clear overwrites it, and only while focused.
- `apps/vault` — Expo Router web app, for manual testing and `E2E_WEB`; screens take navigation callbacks as props (the `app/` route files wire them) so tests render them without a router. The session lives in localStorage and keeps the vault keys only sealed under a non-extractable WebCrypto key (`webKeyStore.ts`); Argon2id is hash-wasm's WebAssembly build.
- The flake builds `web-dist` (the web export) from source with bun2nix over `nix/bun.nix`: run `nix:bun-lock` after every `bun.lock` change.

## CI

- Conventional Commits; a fix closing an issue carries `Fixes #N` in the commit body. Work lands on `dev`; `main` takes only PRs from `dev` (`pr-base.yml`).
- `ci.yml`: `Lint`, `Lint (Rust)`, `Test (Rust)`, `Test (vault-core)`, `Test (app)` (jest + the web export), `End to end (server + CLI)` (the pinned core release's server image and the binaries built here, with the browser checks), `Audit (Rust)` (cargo-deny, `deny.toml`) and `Audit (JS)` (both continue-on-error), chosen by changed paths; a manual run or a release runs everything.
- `release.yml` releases the binaries on a `v*` tag, which must equal `Cargo.toml`'s workspace version (move it by hand; `cargo` updates `Cargo.lock`): `CI`, then `atlas-vault-X.Y.Z-<target>` and `secretspec-provider-atlas-X.Y.Z-<target>` static binaries (musl on Linux, zig for aarch64; as core built them), `THIRD_PARTY_NOTICES.txt` of their crates (`scripts/rust-notices.mjs`), provenance attestations and `SHA256SUMS.txt`, in a GitHub Release with generated notes. A tag with `-` (`vX.Y.Z-rc.N`, tagged on `dev`) is a prerelease, never `latest`; a stable one is tagged on `main` after a `dev` → `main` PR.
- The two known unfixable `bun audit` advisories are `node-forge` (no patched release) and `zod` 3 (fixed only in 4.x; `@expo/cli` needs 3), both in the Expo toolchain and analyzed in `//audit-known` in the root `package.json`; fixable ones go in the root `overrides`, never an ignore list.
