## What this is

A **test harness for Atlas core**, not a product: a password-manager-shaped client that proves core's shared logic — `@atlastodo/client-core`/`@atlastodo/shared` from npm (including `sealPersistence`), the server's vault token policies and the `atlas` CLI — works for an app other than todo. It has no releases, no store presence and no native builds, and must not hold real secrets. The server, the `atlas` CLI and the core packages are in the core repository, [atlastodo/atlas](https://github.com/atlastodo/atlas) (a checkout is expected at `../atlas` by the scripts).

- Bumping the core pin here is how a core change is exercised from the outside: move it, run `test:all`, `lint` and `e2e:cli` (and `E2E_WEB=1`). A failure is a finding about core; fix it in core (a branch in the core repository), not with a workaround here.
- Removed on purpose (2026-10): the Android/iOS build (devenv Android SDK, `build:android*`, `mobile:*`, the Gradle cache workflow and action, EAS, the native Argon2 module, the keychain session, SQLite persistence, the install key, the clipboard's Android flag, store icons and splash), the Android permission allowlist, the release workflow, `version:bump`, release notes, the derived `versionCode` and the web release tarball. Don't bring them back.

## Dev environment

- All dev commands (`test:all`, `e2e:cli`, `lint`, `fmt`, `nix:bun-lock`, `deps:update`, `web:dev`, `web:export`) are devenv scripts in `devenv.nix` — run them inside `devenv shell` (or `devenv shell -- <script>`). The root `package.json` has **no** scripts. (The full suite is `test:all`, not `test`, which collides with the shell builtin.)
- Bun is the package manager (`bun.lock` committed, lockfile version 1 — bun2nix reads no other; CI installs with `--frozen-lockfile`); Node 26 is the runtime. Bun is pinned to **1.4.2** in devenv (the flake's nixpkgs, which `devenv.yaml` follows) and `BUN_VERSION` in `.github/workflows/*.yml`, in lockstep: `deps:update` moves the workflow pins to the Bun that nixpkgs ships.
- One set of pins: `devenv.yaml` takes `nixpkgs` from this repository's flake (`atlas-vault: url: path:.`, `follows: atlas-vault/nixpkgs`), so the shell and the flake's builds share `flake.lock`. Move it with `nix flake update`, then `devenv update` (which copies it into `devenv.lock`); `lint` and CI's `Lint (TypeScript)` fail when `devenv.lock` is behind (`scripts/check-devenv-lock.mjs`).
- TypeScript is 7 (the native compiler) everywhere: the root and both workspaces. Its npm package has no JS compiler API, which is why the linter is oxlint, not ESLint with typescript-eslint.
- The core packages come from npm at an exact version (now `0.1.14-rc.1`): `@atlastodo/client-core` and `@atlastodo/shared` (the vault item rules). They follow the newest core release (rc or stable), moved by `deps:update` (Dependabot ignores them) together with `CORE_VERSION`/`ATLAS_SERVER_IMAGE` in `ci.yml` (the e2e job's server image and CLI binary). The core fixtures the tests replay (`vault_item_vectors.json`, `field_policy_vectors.json`) are read from those packages, so a bump picks them up.
- A server for development: in the core checkout, `devenv up` and `ATLAS_APPS=todo,vault cargo run -p atlas-server`; `EXPO_PUBLIC_API_URL` defaults to `http://localhost:8080`.

- Nothing is held back on purpose. Dependabot (`.github/dependabot.yml`, weekly, to `dev`, a 3-day `cooldown`) covers direct dependencies and Actions; everything else (`devenv.lock`, `flake.lock`, the Bun pins, the whole `bun.lock` with transitives and the `overrides`, the Expo SDK's packages via `expo install --fix`, the core pin, `nix/bun.nix`) is `deps:update` (`scripts/update-deps.sh`), which `deps-refresh.yml` runs weekly and opens as one PR from `chore/deps-refresh`. A new Expo SDK major is a migration, flagged as an issue. `overrides` are ranges, never exact pins.

## Verification

- `test:all` = vitest in `packages/vault-core` (under Bun: `bunx --bun vitest run`) → jest-expo in `apps/vault` (must run under real Node: `bun run test`).
- `lint` = `tsc --noEmit` for both workspaces + `oxlint .` (`.oxlintrc.json`: the typescript-eslint `recommended` rules and react-hooks `rules-of-hooks` (error) and `exhaustive-deps` (warning)) + `prettier --check .` + `scripts/third-party-licenses.mjs --check` + a stale-`nix/bun.nix` check.
- `e2e:cli` (`scripts/e2e-cli.sh`) = a throwaway database, core's `atlas-server` with `ATLAS_APPS=todo,vault`, and the `atlas` CLI: `packages/vault-core/e2e` proves an item the CLI adds shows up in the app's store field for field and the reverse (edits, secret history, trash), that `atlas vault get X --field password` prints exactly what the app stored, that a read-only token made as the app makes it is refused writes by the server (a raw push: 403 `api_token_read_only`), that the server's token-policy errors come back typed, and that an Atlas Todo account gets its vault key on its first vault sign-in. `E2E_WEB=1` also exports the web app, serves it from that server and drives it in headless Chromium (`scripts/e2e-web.mjs`: sign-up, a login with its password masked, search, read-only and writing tokens made in Settings, the CLI both ways, an item written while the sync routes fail surviving a reload and syncing after, the vault's IndexedDB holding no plaintext, lock/unlock, a session past its auto-lock deadline opening locked). Binaries are built from `ATLAS_CORE_DIR` (default `../atlas`) or given as `ATLAS_SERVER_BIN`/`ATLAS_CLI`; Postgres from `E2E_DATABASE_URL` (default the devenv one on 5432). CI's `End to end` job runs the same suites against the pinned core release's image and CLI binary.
- The web app is the only target: `web:export` (or CI's export step) must pass. jest-expo still renders the screens with its default (native) preset; there are no platform files any more, so the web implementations are what the tests run.

## Layout and rules

- `packages/vault-core` — platform-free: `items.ts` (items and folders in a client-core `LocalStore`; every item rule is `@atlastodo/shared`'s `vault.ts` — `newVaultItemFields`, `vaultItemChanges` (secret history), `toVaultItem` — never reimplemented here; `vectors.test.ts` replays core's `vault_item_vectors.json` through the store), `query.ts` (list filters; search never reads secret values), `generator.ts` (CSPRNG only, rejection sampling, no `Math.random` fallback), `totp.ts` (RFC 6238, tested on the RFC's vectors), `autoLock.ts`, `account.ts` (sign-in/up/unlock, opening the vault app key), `apiTokens.ts` (vault tokens), `engine.ts` (the sealed on-disk store + `SyncClient`).
- **No new crypto.** Keys and envelopes are client-core's: the password opens the root (`openAccountKeys`, `ensureRootKey` for an account without one), the root opens the vault app key (`enableApp`/`openAppKey`, app `vault`). The vault key plays the DEK's role in the keyring (envelope kid `"dek"`, scope personal). The todo key is never stored. If core lacks something, change core (a branch in the core repository), don't work around it here.
- Every sync request is vault-scoped: build clients with `createVaultApiClient` (`x-atlas-sync-apps: vault`). A vault session has no legacy plaintext: `setLegacyMigrated(true)`. The server must offer `api_token_policies` (checked at sign-in, `VAULT_SERVER_REQUIREMENTS`).
- Vault API tokens are vault-only (`apps: ["vault"]`), always carry `expires_at` (≤ the policy's `max_lifetime_days`, from client-core's `tokenPolicyFor`) and send `write` explicitly (false unless the user opts in).
- **Nothing decrypted at rest.** The device's op log (`data/persistence.ts`: IndexedDB `atlas-vault-<user>`, in memory where IndexedDB is missing) is passed to `VaultEngine` unsealed, and the engine always wraps it with client-core's `sealPersistence` under `deriveLocalStoreKey(vaultKey, userId)` — never pass a sealed or plaintext-reading store around it. A log that fails with `SealedStoreError` is cleared (ops, cursor, bootstrap) and pulled again (`onStoreReset`, shown as a notice). `engine.stop()` flushes, closes the database and zeroes the derived key; the vault key bytes are never zeroed (an in-flight push could otherwise encrypt under zeros). `sealedStore.test.ts` covers ciphertext on disk, reopen without the network, the wrong key and offline edits across a restart.
- **Locking** (`AuthContext.lock`, `AutoLockGate`) drops the vault keys from memory and from the stored session, unmounts the vault (its decrypted store, every revealed secret; the engine closes the sealed database) and clears a copied secret. Signing out also deletes the database. The session stores `lockAt`; a session restored past it opens locked. Browser tabs follow each other's lock and activity through the stored session. Auto-lock timeout and clipboard timeout are per-device prefs (`lib/prefs.ts`), not synced.
- Clipboard (`lib/clipboard.ts`): a copied secret is cleared after the timeout; the web cannot read the clipboard without a prompt, so the clear overwrites it, and only while focused.
- `apps/vault` — Expo Router web app, for manual testing and `E2E_WEB`; screens take navigation callbacks as props (the `app/` route files wire them) so tests render them without a router. The session lives in localStorage and keeps the vault keys only sealed under a non-extractable WebCrypto key (`webKeyStore.ts`); Argon2id is hash-wasm's WebAssembly build.
- The flake builds `web-dist` (the web export) from source with bun2nix over `nix/bun.nix`: run `nix:bun-lock` after every `bun.lock` change.

## CI

- Conventional Commits; a fix closing an issue carries `Fixes #N` in the commit body. Work lands on `dev`; `main` takes only PRs from `dev` (`pr-base.yml`). There are no tags or releases.
- `ci.yml`: `Lint`, `Test (vault-core)`, `Test (app)` (jest + the web export), `End to end (server + CLI)` (the pinned core release's server image and CLI binary, with the browser checks), `Audit (JS)` (continue-on-error), chosen by changed paths; a manual run runs everything.
- The two known unfixable `bun audit` advisories are `node-forge` (no patched release) and `zod` 3 (fixed only in 4.x; `@expo/cli` needs 3), both in the Expo toolchain and analyzed in `//audit-known` in the root `package.json`; fixable ones go in the root `overrides`, never an ignore list.
